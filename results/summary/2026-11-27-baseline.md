# Baseline: stock xfce4-terminal 1.0.4 on EL8 (2026-11-27)

What the unmodified terminal costs on EL8, measured with the Plan 1 harness. This is the reference that
Plans 2-3 are measured against. Its "five biggest costs" section sets the order of Plan 3's work. EL9
and the CachyOS dev host appear at the end, for reference only.

Every medians table for every configuration is in
[2026-11-27-baseline-medians.md](2026-11-27-baseline-medians.md).

## Setup

- **Platform `el8`** (primary): almalinux:8.10 container, EPEL8 `xfce4-terminal-1.0.4-1.el8` with
  `vte291-0.52.4-2.el8`.
  - Toolkit stack: gtk3 3.22.30, glib2 2.56.4, cairo 1.15.12, pango 1.42.4.
  - X servers: Xvfb 1.20.11 and Xvnc from tigervnc-server-minimal 1.15.0, both 1920x1080.
  - Window managers: mutter 3.32.2 and marco 1.26.2.
- **Image pins** (`bench/pins.json`): nvim v0.12.5, tmux 3.5a and CaskaydiaCove Nerd Font v3.5.1, each
  checked by sha256.
- **Hardware**: one 24-core x86_64 workstation with no GPU, used by every platform. The containers run
  with `--network none`.
- **Matrix, `full` preset** (2015 runs, 13 workloads, 7 iterations each):
  - Displays and encodings:
    - Xvfb;
    - Xvnc with Tight and ZRLE, read by the harness's own RFB client;
    - Xvnc behind the harness's X11 proxy ("x11remote"), which emulates a terminal running on a farm
      node (T2) at RTT 0.25 ms.
  - Window managers: none, mutter, marco with compositing, and marco without it.
  - Terminal: maximised on the 1920x1080 screen, Caskaydia 12 pt. The title bar decides the rows:
    213x54 cells (1920x1043 px) under mutter, 213x55 (1920x1053) under marco, and 213x56 (the whole
    screen) with no WM. Every run records its actual window size and cells.
  - A sensitivity block adds a 120x40-cell window (1082x762 px) and DejaVu Sans Mono 12, on
    Xvnc/Tight/mutter, with 5 iterations.
- **Matrix, `rtt-sweep` preset**: x11remote/Tight/mutter at RTT 0, 0.25, 2 and 20 ms, 5 iterations,
  80 runs.
- **Run health**: 0 errors and 0 drain timeouts in all 2344 records behind this page (both presets,
  both noise checks, and the host runs).
- **Workloads.**
  - Typing (40 keystrokes, 120 ms apart; VNC runs add 20 keys sent from the VNC client):
    - `shell-echo` — tty echo;
    - `nvim-type` — nvim with `number`, `cursorline` and `laststatus=2`;
    - `tmux-type` — typing inside tmux;
    - `tmux-pane-switch` — two tmux panes; every key switches to the other pane;
    - `tmux-type-load` — typing into the top tmux pane while the bottom pane prints output nonstop.
      No VNC keys; the measurement is described below.
  - Bulk output (50 MiB each):
    - `bulk-ascii`;
    - `sgr-color` — 256-colour and truecolour runs;
    - `unicode` — CJK, combining marks, emoji and Nerd Font glyphs;
    - `box-drawing`.
  - Other:
    - `compile-log` — 200k gcc-like lines;
    - `tmux-bulk-split` — 20 MiB into one of two tmux panes;
    - `fullscreen-redraw` — full-screen repaints of the real terminal size at 60 fps for 5 s;
    - `nvim-scroll` — 2000 scroll steps through a 50k-line file.
- **What is measured.**
  - Typing latency: from an XTest key press to the terminal window's next X Damage event.
    - The harness keeps reading damage until the next key is due, and counts separate paints (bursts
      more than 2 ms apart). `latency_multi_paint` counts keys that were followed by a later, separate
      paint. Such a key's first damage might not be the echo.
    - For `tmux-type-load`, only damage inside a 20-cell area around the typed pane's key marker
      counts, and only once that area's pixels have actually changed. The load repaints most of the window 8-10 times a
      second, so the first damage anywhere would mean nothing.
  - End-to-end latency ("e2e"): from a VNC key event to the framebuffer update that shows it.
  - Throughput: payload bytes over total time, including the drain.
  - CPU from `/proc/<pid>/task/*/schedstat`, in ns, for the terminal and the X server. Both are read
    over the same window, from just before the workload starts until the screen has settled after it.
  - Damage area: how many pixels the X server reports as repainted.
  - VNC bytes and CopyRect area.
  - On the X11 link (x11remote only): bytes, requests and replies. Every reply is a round trip, but the
    client does not always wait for it.
  - Workload metrics cover the workload phase only. Startup settles first, then the counters are
    reset.
  - Each run is reduced to its own median first. Every figure on this page is the median of those
    per-run medians.

## The five biggest costs (input to Plan 3's ordering)

Ranked by what a person typing or reading output over a remote display gets:

1. **VTE 0.52 takes 25.6 ms from key to paint, on every display and every window manager.**
   - The figure is the same on Xvfb, on Xvnc with either encoding, and with or without a compositor.
     So it comes from the terminal, not from the display path.
   - It is the echo itself: none of the 18600 typing keys in the full preset was followed by a second
     paint (2 of 6200 pane switches were).
   - It is about 73% of the 35 ms end-to-end keystroke over VNC.
   - The host's VTE 0.84 paints the echo 1.0-1.2 ms after the key (see Other platforms).
   - **Plan 2's VTE 0.84 back-port is expected to remove most of this cost.** Plan 2 must confirm
     that it does so on GTK 3.22.
2. **A keystroke takes 54-71 ms while another tmux pane is printing output.**
   - That is 2.1-2.8 times the idle figure. It is what typing feels like while a build log scrolls.
   - It is 71 ms on Xvfb, and on every display with marco compositing. Otherwise, on Xvnc it is
     64.5-69.5 ms with Tight and 54-59 ms with ZRLE.
   - Each configuration's runs agree to within 3 ms (p10 to p90), so these differences are real. Why
     a busier display path lowers the figure is not yet known.
   - **On the host, VTE 0.84 takes 205 ms here**, three times EL8, even though it paints an idle echo
     in about 1 ms. EL9's VTE 0.64 takes 63.7 ms.
   - So Plan 2's back-port could make this worse. Plan 2 must measure it on EL8 before anything else,
     next to damage per key. Plan 3 needs to show a keystroke's echo ahead of queued output.
3. **marco with compositing adds about 15 ms to every keystroke as the VNC client sees it.**
   - End-to-end latency is 50 ms with marco compositing, 34-35 ms with marco without compositing or
     with no WM, and 35-40 ms with mutter. A pane switch shows 16 ms (52.6 against 36.3 ms).
   - The terminal paints just as fast under every WM (25.6 ms each). The delay is between the
     terminal's paint and the screen, so this is a desktop setting for MATE sessions, not terminal
     work.
4. **Bulk output runs at 11-36 MB/s and uses 0.3-3.9 s of terminal CPU per run.**
   - `unicode` is the slowest at 11.5 MB/s with 3.9 s CPU, then `bulk-ascii` at 14.6 MB/s with
     2.7 s and `sgr-color` at 21.2 MB/s with 2.0 s.
   - The X server adds 0.62-0.86 s on Xvnc for those three.
   - On the host, VTE 0.84 does `bulk-ascii` at 76 MB/s with 0.55 s CPU. EL9's VTE 0.64 does
     20.4 MB/s. So this is mainly Plan 2 again.
5. **The display receives far more new pixels than the content needs.**
   - **No scroll-by-copy.** CopyRect area is 0 in all 1651 VNC runs. VTE 0.52 never moves pixels with
     a copy, so every scrolled frame is new pixels to the VNC encoder.
     - Per run over Tight: `sgr-color` sends 15.3 MiB, `bulk-ascii` 9.6 MiB, `unicode` 7.8 MiB,
       `tmux-bulk-split` 2.7 MiB and `compile-log` 2.0 MiB.
     - Scrolling with XCopyArea would let Xvnc send CopyRect instead, and NoMachine and ETX have
       equivalent copy primitives.
     - This is Plan 3 work, since a VTE upgrade does not change it.
   - **Keystrokes in full-screen apps repaint most of the window.**
     - `nvim-type` damages 1.86 Mpx per key, 93% of the window, on Xvfb and Xvnc alike. A tmux pane
       switch damages 1.04 Mpx, about half the window. `shell-echo` damages 40 kpx, one cell row.
     - VNC bytes stay small (99 B per nvim key) because TigerVNC compares framebuffer contents. The X
       server still does 3x the work of a shell echo (0.171 against 0.058 s per 60 keys).
     - Encoders that trust the damage region, rather than comparing pixels, pay the whole area on every
       key.
     - On EL9 and the host, even a shell echo damages about 1 Mpx per key (see Other platforms).
     - Two jobs follow. Plan 3 should invalidate only the cells that changed. Plan 2 should check that
       its back-port does not bring the newer platforms' behaviour to EL8.

Not in the top five:

- **Remote X at the real farm RTT.** At 0.25 ms a keystroke costs one extra round trip (+0.3-0.6 ms),
  throughput does not change, and startup grows by about 43 ms over the zero-delay proxy.
- **Remote X at 20 ms.** These costs grow with RTT: one RTT per keystroke, `nvim-scroll` 3.4x slower,
  bulk throughput down 11%, and startup at 1.8 s. That matters for a WAN, not for the farm.

Not yet measured: the spec's other workloads are in the list at the end of this page. They must be
measured before Plan 3's order is final.

## Surprises

- **CopyRect is 0 in every run.** This was expected for VTE 0.52, and it is now measured: see cost 5.
- **The latency floor is the terminal's own**, the same 25.6 ms on Xvfb as on VNC. This also makes
  `latency_ms` blind to display-side improvements. Watch e2e latency for those.
- **Typing under load gets faster when the display path is busier.** ZRLE, which costs the X server
  more to encode, gives 54-59 ms where Xvfb gives 71 ms. One guess is that a slower display slows the
  output in the other pane. This is untested.
- **The newer VTE is three times slower at typing under load** (205 ms on the host) while being over 20
  times faster at an idle echo (1.1 against 25.6 ms).
- **marco's compositor, not compositing as such, costs about 15 ms end-to-end.** mutter composites
  too, and costs 0.8-3.7 ms.
- **In nvim, each keystroke repaints most of the window, and a tmux pane switch half of it** (cost 5).
  On EL9 and the host even a shell echo repaints about 1 Mpx (Other platforms).
- **`fullscreen-redraw` does not discriminate on EL8.** Every configuration sustains its 60 fps. What
  differs is X server CPU: 2.0-2.5 s per 5 s on Xvnc with Tight, against 0.48-0.67 s on Xvfb.
- **Launch time is bimodal and depends on the window manager.** Startup is informational: it is not a
  project goal, so it is never flagged.
  - Without mutter, on Xvfb and Xvnc, launches land in two clusters near 54 and 59 ms.
  - With mutter on Xvnc they spread from 106 to 306 ms (median 211). On Xvfb, mutter adds 21 ms.
- **Results drift between sessions.** Two separate invocations of the same configuration differed by
  10-17% on startup, VNC bytes and X server CPU, while the spread within one invocation was 1-5%.
  That is why builds are only ever compared interleaved in one invocation.
- **The number of startup replies depends on link timing**: 145 through the zero-delay proxy, 143 at
  0.25 ms, 129 at 2 ms and 126 at 20 ms.
- **"Maximised" is three sizes.** The title bar takes 37 px under mutter and 27 px under marco, so the
  same screen holds 54, 55 or 56 rows. Every run records the cells it actually had.

- **Latency.** VTE 0.64 keeps EL8's floor (26.4 ms). VTE 0.84 paints the echo in 1-2.4 ms.

## Noise check and method changes

Before this baseline, the harness was checked against itself: the same binary under two build names
(`baseline` and `baseline-twin`), interleaved. The check went through several rounds, and each round
found a cause that was fixed rather than covered by raising the threshold. The 5% threshold never
changed.

- **Session drift** (10-17% between invocations): builds are now compared in one interleaved
  invocation, never across separate runs.
- **CPU tick quantization** (10 ms ticks): CPU now comes from per-thread `schedstat`, in ns.
- **Lost CPU of exited threads**: a GLib pool thread exiting mid-run took its earlier CPU with it. The
  per-thread readings are now remembered, so totals never go backwards.
- **Startup leaking into workload metrics**: payloads wait for a go file. The runner lets startup
  settle (300 ms quiet), resets every counter, and then starts the workload.
- **Order bias**: builds alternate A-B / B-A, and with more than one build the iteration count rounds
  up to even.
- **Frame-phase components**: elapsed/drain splits, rect, update and damage-event counts, CopyRect
  area, and damage area for throughput workloads are informational. The outcomes they add up to stay
  gated.
- **Bimodal launch time**: `startup_ms` is informational. `startup_x11_replies` stays gated.
- **X11 proxy timing**: the proxy's event loop rounded delays up to whole milliseconds, so RTT 0.25 ms
  behaved like about 2 ms. It now uses `select()`, which has microsecond timeouts.

A whole-branch review then changed what is measured. Every number on this page was re-measured after
these changes:

- **Per-run medians.** Each run is reduced to its median before runs are compared, so the noise band is
  the run-to-run spread. Pooling every keystroke had made it keystroke jitter.
- **Stricter gate.**
  - A cost that was 0 in the baseline is flagged when the candidate rises above the baseline's p90.
  - Runs that errored are left out of the medians.
  - More failed runs or drain timeouts in the candidate is flagged, and so is a gated metric that the
    candidate lacks.
  - The report refuses empty inputs, and inputs that mix builds without `--base-build`/`--cand-build`.
- **"Large" is maximised.** The plan's 236x62 cells did not fit the 1920x1080 screen, so the window's
  real size depended on the WM, and `fullscreen-redraw` scrolled. Records now carry the window's
  pixels and cells, and `fullscreen-redraw` draws the terminal's real size.
- **Terminal CPU includes the drain**, over the same window as X server CPU. It used to stop at the
  end of the payload.
- **Paint counting.** Latency now counts separate paints per key, and `latency_multi_paint` is gated.
  Typing under load checks pixels in the typed area.
- **Two workloads added**: `tmux-pane-switch` and `tmux-type-load`.

Twin checks on this data:

- **el8**: 73 gated rows, 0 flagged, 3 that exceeded their band in the twin's favour.
  - `compile-log` VNC bytes and X server CPU fell 9.5-9.7% together: the twin's run was 10.7% shorter
    (throughput +4.8%, inside the threshold), so it sent fewer frames for the same output.
  - `box-drawing` VNC bytes fell 9.7%, against a 9.5% band.
- **el9**: 73 gated rows, 0 flagged, 1 exceedance in the twin's favour (`box-drawing` VNC bytes 6.0%
  against a 3.6% band).

The same movements the other way would have been flagged. So the protocol for Plans 2-3 stands: a flag
is acted on only after the flagged configuration is re-run interleaved with `--iterations 8` or more,
and still flags.
